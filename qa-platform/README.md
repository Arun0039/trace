# Trace · AI QA Test Management Platform MVP

A local-first QA workspace for project-scoped requirements, test cases, execution tracking, lightweight bug tracking, coverage, and CSV reporting. The core server, database, and UI use Python's standard library. Optional AI analysis uses the Vercel AI SDK through a small Node.js provider adapter.

See [the architecture audit and migration mapping](docs/ARCHITECTURE.md) for the current codebase assessment and staged refactoring plan.

## Quick start (Windows)

1. Install Python 3.10 or later from [python.org](https://www.python.org/downloads/) and enable **Add Python to PATH**.
2. Open PowerShell or Command Prompt and enter this folder:

   ```powershell
   cd "C:\path\to\QA Tracker\qa-platform"
   ```

3. Copy `.env.example` to `.env`. Set `QA_ADMIN_PASSWORD` to a unique password with at least 12 characters. Generate a 64-character hexadecimal encryption key (for example, run `python -c "import secrets; print(secrets.token_hex(32))"`) and set it as `QA_AI_ENCRYPTION_KEY`. Keep both values private and do not commit `.env`. The Windows launcher checks for the required Python packages and installs any that are missing using the same Python interpreter it uses to start the app.
4. For Gemini or another SDK-backed provider, install Node.js 22 or later and run `npm ci` from `qa-platform`. Local deterministic mode does not require Node.js or an API key. Ollama additionally requires its local server and selected model to be running.
5. Start the app:

   ```powershell
   .\start-qa-platform.bat
   ```

   The launcher checks Python's `py` and `python` commands and common per-user/system install folders. If Python is missing and `winget` is available, it offers to install Python 3.13 for the current user; otherwise it provides the official download link. Before starting, it verifies `cryptography` and `pypdf`, bootstraps pip if needed, and installs `requirements.txt` when either package is missing. If installation fails, it displays the pip error and a command to retry with the selected interpreter. You can also run `py -3 app.py` or `python app.py` from this folder after installing the dependencies. The launcher keeps its console visible if Python exits, so you can copy the startup error.
6. When startup succeeds, the app prints its local URL and tries to open the browser automatically. If the default port is already in use, the app selects another available port; use the URL printed in the console rather than assuming port 8001. Sign in under **Settings → AI Module** using `QA_ADMIN_PASSWORD`, configure a provider, save, and test its connection. Keep the console open while using the app; Ctrl+C stops the server.

The app listens on loopback (`127.0.0.1`) only by default. Structured data is stored in `qa_platform.sqlite3` alongside `app.py`; each project has a separate folder under `storage/projects/{project_id}/` for requirement uploads, application files, and CSV exports. Deleting a project removes its SQLite records and moves its folder to `storage/archived-projects/` so the files are retained. To use a different database location, set `QA_PLATFORM_DB` before startup. `QA_HOST` and `QA_PORT` can also override the bind address and port; do not expose this development MVP to an untrusted network.

## Using the workspace

- **Project** is the primary module and opens the searchable project list, with status filtering and generated project ID, project key, status, and created/updated dates. Create a project to open its details page, or use View, Details, Edit, and Delete from the list. Project edits validate required fields and unique project keys; deletion confirms the action, removes associated SQLite records, and archives the project folder so uploaded files and exports are retained.
- Each selected project has its own child modules: **Requirement**, **Test Case**, **Application**, **API Documentation**, **App Analysis**, **Bug Tracker**, and **Project files**. The child modules remain associated with the selected project's SQLite ID and appear in the project navigation while a project workspace is open. **Dashboard (Beta)** and **Settings (Beta)** are workspace modules. Settings contains the **AI module** for provider configuration and connection testing, and **Archive** for browsing retained folders from deleted projects. Project setup records product type, project name, description, version, environment, QA owner, and active/inactive status.
- The **Archive** view lists retained project folders and their archive dates. It does not restore deleted SQLite records; files remain in the local `storage/archived-projects/` directory.
- Follow the project flow: (1) paste text or upload a `.pdf`/`.docx` (maximum 5 MB), `.csv`, `.txt`, or `.md` (maximum 1 MB); (2) review the rule-based `EXTRACTED` records separately from `AI SUGGESTION` content and confirm; (3) review each extracted record and mark it **Reviewed** before test-case generation; (4) explicitly Accept, Edit, or Reject each AI suggestion; (5) generate linked test-case drafts; (6) upload the finalized application ZIP and validate requirement coverage against its source. Only deterministic source extraction is stored as an extracted BRD requirement. An AI analysis report and proposed requirements remain suggestions and never replace extracted records. Suggestions retain their original content, exact source evidence when available, reason, related requirement, status, and reviewer decision history. Accepting a suggestion creates a separate requirement with AI origin and approval provenance; re-importing a BRD does not overwrite prior requirements, suggestions, or reviewer decisions. Test generation excludes pending/rejected suggestions and includes an accepted suggestion only after its explicit approval. Rule extraction supports structured headings, labeled requirements, CSV feature rows, and explicit requirement-like statements; it does not turn an entire unstructured document or a heading alone into a confirmed requirement. The analysis report is labeled `AI SUGGESTION` or `NEEDS REVIEW` and does not establish confirmed source facts. Cancelling the confirmation leaves the document and extracted requirements unsaved. View saved analyses from **BRD Documents** or download them as Markdown. Requirements can be deleted; linked cases remain but are unlinked.
- PDF imports extract embedded text only; scanned/image-only PDFs must be OCR-processed before upload. Mark a requirement **Rejected** to exclude it from approval; only **Reviewed** requirements are eligible for test-case generation.
- Generate test cases from the **Test Case** module after the source requirements have been reviewed and marked **Reviewed** (the app's approval state). Requirements marked **Needs review** are excluded; selecting one explicitly returns an error. Accepted AI suggestions are eligible only after explicit acceptance and retain their AI origin, approval status, and suggestion ID in test-case traceability and CSV exports. The configured provider receives the workspace skill at `.github/skills/requirement-test-case-generation/SKILL.md`, which guides generation of sufficient, non-duplicative positive, negative, boundary, validation, permission, error, integration, and quality-focused cases only where the requirement supports them. The application assigns sequential test-case IDs and requires every generated case to link to a reviewed requirement. Cases store requirement/use-case traceability, origin and approval provenance, type, scenario, preconditions, test data, steps, expected result, and priority; execution status and actual results remain QA-entered. Generation reports coverage among reviewed requirements, including uncovered requirements. Use the local deterministic generator or the configured AI provider; exact repeats are skipped and each request is capped at 300 cases. Review and edit all cases before execution. Existing cases are preserved during regeneration for safe manual review; changed or potentially obsolete cases are not silently overwritten or deleted.
- The **Test Case** module also offers **AI-assisted generation without a BRD**. Paste feature notes, workflows, draft requirements, or existing cases, select Functional, Non-Functional, Sanity, and/or Smoke coverage, then submit with a configured model-based provider. The model reports explicit facts, assumptions, gaps, duplicate/overlapping coverage, unclear points, and clarification questions separately. If the source is insufficient, it returns questions without creating cases. Generated drafts retain an input quotation when available, category, positive/negative classification, assumptions, and an editable title alongside the usual execution fields. The original text remains in the generator while navigating within the current page session; it is not saved as a requirement. CSV exports include the case category and traceability fields. Local deterministic mode remains available for BRD-based generation only.
- Import a local `.json` OpenAPI 3.x or Swagger 2.0 specification from **API docs** to build a searchable project endpoint inventory. The app validates the document and records operations, summaries, operation IDs, tags, and the source document name; it never fetches a URL.
- Upload a finalized developer build `.zip` from **Applications** for a project-scoped file inventory and bounded static analysis. Use **Validate requirement coverage** on an upload to compare every project requirement against source excerpts using the configured cloud/SDK AI provider; deterministic Local mode does not perform AI-assisted coverage review. At most 80 excerpts and 300 KB of source text per model request are sent (requirements are processed in batches of 100); cited evidence must match text in the uploaded files. Reports are marked stale when requirements change and should be rerun. Results are AI-assisted static estimates, not proof of runtime functionality or correctness. ZIPs are limited to 25 MB, 3,000 entries, 100 MB total extracted content, and 20 MB per file. Unsafe paths, symbolic links, duplicate/colliding entries, unsupported compression, encrypted members, and excessive compression are rejected.
- Configure providers from **Settings → AI Module** after signing in as the local Admin. Supported choices are Local deterministic, Ollama (loopback OpenAI-compatible API), Google Gemini (default model `gemini-2.5-flash`), and Other (an OpenAI-compatible HTTPS endpoint). Google and Other require an API key; Ollama does not. The browser never receives provider keys: credentials are encrypted in SQLite with `QA_AI_ENCRYPTION_KEY`, which must remain stable while those credentials are stored. A lost or changed key makes existing credentials undecryptable. Gemini and compatible-provider requests send requirement text and bounded source excerpts to the selected endpoint; use Local or a trusted local Ollama instance for data that must remain local. The existing API is synchronous JSON and does not expose streaming. Missing, invalid, and connection-failure cases are surfaced by the settings and analysis APIs.
- Execute a case with one of: Not Executed, In Progress, Pass, Fail, Blocked, or Skipped. Each save creates an execution record; the latest result appears in the case list and dashboard. Optionally attach PNG, JPEG, GIF, or WebP screenshot evidence (maximum 5 MB per image) while recording an execution. The case list links to evidence previews and downloads.
- Log bugs and link them to cases, especially failed cases. Update bug status, severity, priority, and assignment.
- Use **Export report** to download a UTF-8 CSV that opens in Excel. It contains test cases, evidence references for each case's latest execution, a complete execution-evidence reference section, a requirement coverage matrix, and a bug summary. CSV is used instead of `.xlsx` to avoid third-party dependencies. Test cases include case, requirement, and optional use-case IDs; title, scenario, category, type, positive/negative classification, priority, preconditions, test data, assumptions, source reference, description, steps, expected result, status, and actual result. Edit cases to update their fields, status, or actual result, and delete cases with their execution history.

## Static application analysis with REA

Select **App analysis** inside a project to statically inspect an application directory or `.asar` file using the sibling `rea/` package. This integration invokes REA's documented `analyze-javascript-application` CLI command through a local Node.js process; it is **not an MCP integration**. REA and its compiled runtime/dependencies must already be available in `../rea/`. The app does not install or build REA automatically. The runtime status endpoint and page explain missing Node.js, unsupported Node versions, missing builds/dependencies, and unsafe network binding.

Enter the exact absolute path as seen by the computer running the QA server. The path must identify an existing directory or `.asar` file. This separate REA workflow does not accept ZIP uploads or execute application code. Analysis runs in a background worker, one at a time, with a 10-minute timeout and bounded CLI output/evidence bundle size. The complete REA Evidence is written to a unique temporary bundle path and deleted after REA returns its summary. Project-scoped SQLite history retains the input path, status, bounded summary, and failure message—not the full Evidence bundle.

The summary presents only values reported by REA, such as the artifact SHA-256 and format, source/module statistics, Electron boundary counts, route statistics when present, and explicit limitations. Missing summary fields remain absent; they are not interpreted as zero or as proof of absence.

## Data and safety notes

- SQLite is initialized on startup with foreign-key enforcement, project-scoped relationships, and parameterized user-data queries. Additive schema initialization creates API-document, endpoint-inventory, execution-evidence, application-analysis, application-upload, and requirement-document tables and fields for existing databases.
- Requirements accept `.docx` uploads up to 5 MB and `.txt` / `.md` documents up to 1 MB of text. DOCX parsing reads only the bounded `word/document.xml` member without extracting or opening embedded content. API specifications accept local `.json` uploads up to 1 MB and must declare OpenAPI 3.x or Swagger 2.0 with valid document metadata and paths. No URL import, remote fetch, uploaded code execution, or specification dereferencing occurs.
- Application ZIPs are untrusted input. Members are fully preflighted before extraction, extracted into a unique staging folder and atomically moved into `storage/projects/{project_id}/applications/{upload_uuid}` beside the SQLite database. The database stores the project-scoped inventory and static findings; API responses do not reveal the server storage path. Source inspection has per-file, total-byte, file-count, and findings limits, so results may be incomplete. ZIP upload API: `POST /api/projects/{id}/applications/import?filename=client.zip` with raw ZIP bytes and `Content-Type: application/zip` (25 MB maximum); JSON/base64 uploads remain supported. List or retrieve records through `GET /api/projects/{id}/applications` and `GET /api/projects/{id}/applications/{upload_id}`.
- `GET /api/ai/settings` returns provider metadata without credentials. `POST /api/ai/settings` saves encrypted provider settings and `POST /api/ai/test` checks the selected provider. These routes and AI operations require an Admin session from `POST /api/auth/login`; the session is local, in-memory, HttpOnly, and expires after 12 hours. Test-case generation accepts `{"generator":"deterministic"}` or the selected provider ID (`google`, `ollama`, or `openai-compatible`) at `POST /api/projects/{id}/test-cases/generate`. Existing BRD preview/confirmation and test-case response shapes remain intact.
- Evidence is validated by declared image MIME type, file signature/structure, dimensions where available, and a 5 MB size limit, then stored as a BLOB in SQLite under its project and execution. The application does not serve evidence cross-project. Request bodies are capped at 27 MB to support raw ZIP uploads.
- CSV exports are downloaded as before and also saved to `storage/projects/{project_id}/exports/project-report.csv`. `DELETE /api/projects/{id}` deletes the project's SQLite records and archives its project folder instead of deleting its files.
- The web app is a single-Admin local MVP without cloud sync. It listens on `127.0.0.1` by default; Admin login is accepted only from loopback clients. REA analysis is disabled if the server is configured to bind beyond loopback; do not expose the app to an untrusted network. Keep the database and `.env` private. Back up the database and encryption key together by stopping the app before copying them.

## Tests

Run the standard-library test suite from this folder:

```powershell
py -m unittest discover -s tests -v
```

Run the Vercel AI SDK adapter tests with `npm test`.

Application-analysis API: `GET /api/rea/runtime` checks local CLI readiness; `POST /api/projects/{id}/analyses` starts a job with `{"input_path":"<absolute local path>"}`; `GET /api/projects/{id}/analyses` lists that project's history; and `GET /api/projects/{id}/analyses/{analysis_id}` reads one project-scoped result.

Requirement-document API: `POST /api/projects/{id}/requirements/import` accepts `{"filename":"requirements.md","content":"..."}` for TXT/Markdown, or `{"filename":"requirements.docx","document_data":"<base64 DOCX bytes>"}` for DOCX. The first request returns a server-issued preview ID; confirm with the same source and `{"preview_id":"..."}`. The server reuses only its own preview data and persists deterministic extractions as requirements, with AI proposals in a separate review queue. `GET /api/projects/{id}/requirements/suggestions` lists proposals and approval history; `PATCH /api/projects/{id}/requirements/suggestions/{suggestion_id}` accepts `{"action":"accept"}`, `{"action":"reject"}`, or `{"action":"edit","content":{...}}`. Accepting creates an AI-origin requirement with reviewer provenance. Imports use the configured provider by default (`"generator":"auto"`); pass the selected provider ID to require it, or `"generator":"deterministic"` to force local extraction. `POST /api/projects/{id}/requirements/analyze` re-runs module classification for existing requirements; Local uses the deterministic classifier. `GET /api/projects/{id}/requirements/documents` lists project-scoped imports; `GET /api/projects/{id}/requirements/documents/{document_id}` downloads the stored original.

Test-case generation API: `POST /api/projects/{id}/test-cases/generate` with `{}` generates drafts only from project requirements. Optionally pass `{"requirement_ids":[1,2]}` to select requirements. The response reports created cases, duplicate skips, and whether the 300-case limit was reached.

Code coverage API: `POST /api/projects/{id}/applications/{application_id}/validate-requirements` asks the configured non-Local AI provider to compare project requirements with a bounded set of uploaded source excerpts. Results and exact-snippet citations are validated and retained with that application upload. Local deterministic mode reports that it cannot perform this AI-assisted static check; this is not a runtime test.
